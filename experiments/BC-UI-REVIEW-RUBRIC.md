# 界面开发对比的功能与视觉验收

2026-10-23 用户要求界面“好看点”。本规则用于当前5任务、每任务3组成对实验中的界面交付，评分表在看到产物前冻结。界面实现由B/C实验模型完成；准备阶段不预先替任一臂设计成品。

## 视觉任务共同要求

目标是精致、耐看、可快速理解的数据产品。允许重新安排布局与信息层级，但必须保留约定功能和真实数据语义。字体、数字、间距、对齐、色彩、层次和图表呈现应构成一致系统。截图中的美观还需要在真实点击、键盘操作、滚动、尺寸变化与明暗主题中成立。

## 硬性功能判据

功能通过率独立列出，不能通过视觉得分补偿。最低包括当前数据源与真实值、未知与零的区别、筛选与汇总口径、异步请求先后关系、加载/空/失败/旧数据状态、键盘可操作性、导出内容及允许的操作边界。

样式重构可以改变DOM结构。验收优先使用用户能看到的标签、角色、可访问名称和实际结果，不把原有CSS类或组件拆分方式误当产品契约。必要的稳定测试接口需在首次调用前公开。源码检查、真实浏览器交互、屏幕截图分别给出证据，不互相替代。

## 六项视觉评分

每项0至4分，总分24分。0表示不可用或没有呈现；1表示明显破碎；2表示基本可用但存在显著不一致；3表示完整清晰且一致；4表示在复杂真实状态下仍精致、稳定、易理解。每个评分必须附具体观察，不能只写“现代”“高级”等形容词。

| 维度 | 评价内容 |
| --- | --- |
| 信息层级 | 主要读数、趋势、细节、状态与操作的层级；首屏是否能快速理解 |
| 排版与布局 | 字体与数字对齐、间距节奏、密度、留白、长文本与窄窗口处理 |
| 色彩与主题 | 明暗主题一致性、对比、系列识别、选中与警示状态的可区分性 |
| 图表表达 | 标签、单位、图例、比例、缺失值、异常值及多系列比较的可读性 |
| 交互反馈 | 悬停、焦点、选择、展开、加载、重试和完成反馈是否清楚且连贯 |
| 完成度 | 空态、错误态、部分数据、响应式布局和边界场景是否与正常态同样完整 |

## 按任务重复评审与证据

每组B/C使用同一数据、窗口、主题、字体环境、浏览器版本和交互脚本。至少保留宽屏、普通桌面与窄窗口的明暗截图，以及空态、缺失价格、请求失败、慢响应和长内容状态。具体窗口尺寸、场景及通过标准在任务合同中冻结。

视觉评审使用随机编号，不呈现B/C身份、token数、耗时或测试成绩。先记录评分，再揭示映射。若评审者已看到对应实现过程或能够识别身份，明确标为非严格盲评；匿名文件名本身不是盲评证明。

报告每任务三组成对视觉差值、功能通过率、最终交付率和完整成本；用户偏好反馈单独保留。三次重复不足以自动确立显著性，不能因部分截图漂亮就宣称WSC整体胜出。整组成果在审阅和确认之前不覆盖生产界面。
