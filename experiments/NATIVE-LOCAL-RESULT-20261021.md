## 停止原因与设计问题

B/C 的基础提示词哈希、动态工具注册、模型、强度、工作目录及沙箱配置一致，但原生启动生成的第一条 developer 消息不同。B 包含 Pages、Sites、Work Pets、插件管理等技能和推荐插件列表；C 缺少这些条目，技能路径别名也随之变化。这是模型可见内容差异，不能当成无关传输元数据忽略。

C 的 stderr 同时记录远程插件目录/featured 请求失败。这支持“原生插件发现结果不一致”的定位，但没有证明具体网络故障根因。实验驱动在 C 的 `turn/start` 之前拒绝准入；C 的真实 rollout 中 `token_usage_record` 为 0，亦无 C 推理尝试登记。

当前驱动的设计不足是：两臂分别创建原生 app-server，并在 B 结束后才核对 C 的实际启动材料。相同启动参数不足以保证动态发现的材料相同，因而可能先消耗 B 再发现不可比。下一组实验应在任何付费请求前完成两臂真实宿主材料的共同准入，并控制会话生命周期；不能通过删改原生提示词、隐藏目录差异或只重跑 C 来补成有利结果。此项后续改造和新的付费对照未执行。
