# WSC 验收矩阵（预注册草案）

2026-10-28。把讨论过的臂、任务、指标、闸门、预算固化成一张可执行的表。**开跑前这份表不能再改**，改了要留版本记录。

## 一、臂设计

核心是一个 2×2，加两条外部参照。

| 臂 | 压缩触发 | 压缩材料 | 回查工具 | 回答什么问题 |
| --- | --- | --- | --- | --- |
| **A** | 不压缩 | — | 无 | 任务本身能不能做完（上限基线） |
| **B** | 原生默认阈值 | 原生 | 无 | 和现状比如何（系统级对照） |
| **B′** | 原生，**与 C 同触发点** | 原生 | 无 | 去掉时机差异后的原生基线 |
| **B′+r** | 原生，与 C 同触发点 | 原生 | 有 | 只加一个检索工具能拿到多少 |
| **C−r** | 原生，与 C 同触发点 | **WSC** | 无 | WSC 的材料/表示贡献 |
| **C** | 原生，与 C 同触发点 | WSC | 有 | 完整方案 |

分解方式：

| 差值 | 含义 |
| --- | --- |
| `C − C−r` | 回查机制在 WSC 材料上的贡献 |
| `C−r − B′` | 材料/表示贡献（去掉回查后） |
| `B′+r − B′` | 纯工具贡献（原生材料上） |
| `C − B` | 系统级总差异（含时机差异） |

**触发点写死**：所有臂在 input tokens 达到上下文窗口 **70%** 时压缩，并记录触发时的实际 token 数。B 用原生默认阈值，单独报告它实际在多少 token 触发。

**归因边界**：这套设计最多能分离"材料"与"回查"两项。状态管理（understanding + 发布协议）无法单独关闭，只能打包进"材料"一并报告，不假装三分。

## 二、任务集

五个独立任务，覆盖不同历史结构，每个任务配一个程序化验收器：

| 编号 | 任务 | 历史结构特点 | 验收方式 |
| --- | --- | --- | --- |
| T1 | 修复失败测试 | 长工具日志 + 反复失败的尝试 | 目标测试通过 + 其他测试不回归 |
| T2 | 改 API 签名 | 同一文件多版本读取 | 调用点全部更新 + 类型检查通过 |
| T3 | 数据库迁移 | 旧决策被新决策覆盖 | 迁移脚本可重放 + 表结构断言 |
| T4 | UI 功能开发 | 大 JSON 配置 + 截图证据 | 交互断言 + 关键文本存在 |
| T5 | 多阶段脚本 | 中间产物交接、跨阶段引用 | 端到端产物校验 |

**依赖历史的证明**：每个任务额外跑一次"清空历史、只给最后状态"的对照。若该对照也能通过，说明任务不依赖历史，该任务作废重设计。

## 三、压缩链

同一会话内连续压缩 **6 轮**，检查点设在第 **2 / 4 / 6** 轮。

| 项 | 配置 |
| --- | --- |
| 臂 | B′ 与 C（只跑两条，控制预算） |
| 任务 | T3（历史覆盖最典型）+ T1（失败重试最多） |
| 每轮注入 | 新事件 + 一次状态更新 + 一次相反陈述（构造"新旧并存"） |
| 每检查点 | 重跑第一、二类测试 |

**失效事实的判法**：每个检查点问两个问题——"当前状态是什么"必须用新值；"当时怎么定的"必须用旧值。答错方向分别计入"过期状态误用"与"历史失真"。

## 四、指标与计算

| 指标 | 计算 | 主/辅 |
| --- | --- | --- |
| 任务成功率 | 验收器全通过记 1，否则 0；按任务等权平均 | **主** |
| 关键约束违规数 | 预定义约束清单逐条判定，计数 | **主（护栏）** |
| 证据支持率 | 产物中带可核对 `source_id` / 字段路径的断言数 ÷ 总断言数 | **主（WSC 独有）** |
| 无依据结论率 | 1 − 证据支持率（仅统计要求引用的产物） | 主 |
| 历史状态准确率 | 预定义状态问题的正确答案比例 | 辅（解释用） |
| 过期状态误用率 | "当前状态"问题用了旧值的比例 | 主（长期） |
| 恢复调用次数 | 冷层读取工具的实际调用数 | 辅 |
| 完整链 token | 拆 uncached / cached / output 三列；压缩自身计入 | **主（成本）** |
| 端到端耗时 | 墙钟，含压缩与恢复 | 辅 |
| 单位成功成本 | 总 token ÷ 成功任务数 | **主（成本）** |

三条硬规矩：

1. **字节压缩率不进结论**，只作附录。
2. **答案正确 ≠ 历史恢复成功**：答对但没引用来源，证据支持率记 0。
3. **无依据结论只能靠引用格式判定**：任务输出必须带 `source_id` 或字段路径，验收器核对能否在来源里找到对应字节。做不到就是无依据。

## 五、三道闸门

| 闸门 | 条件 | 不通过的处置 |
| --- | --- | --- |
| 第一关 不变量 | 来源、版本、状态、发布协议的关键不变量全过 | 任一伪造来源或错误覆盖 → 直接不通过，其他分数不抵消 |
| 第二关 任务能力 | C 成功率 ≥ B′ − 5pp，且约束违规数 ≤ B′ | 不通过则结论为"无任务收益" |
| 第三关 长期与成本 | 6 轮链上每个检查点退化 ≤ 2pp；单位成功成本 ≤ B′ × 1.5 | 超阈值可接受，但必须单列"收益/代价"结论 |

阈值必须在开跑前写进本节，跑完不得调整。

## 六、预算

| 项 | 上限 |
| --- | --- |
| 单次任务运行 | 3M tokens / 120 响应 / 1800 s |
| 单次链运行（6 轮） | 6M tokens / 240 响应 / 3600 s |
| 单臂总量 | 15M tokens（超出即停，不追加） |
| 失败重试 | 不自动重试；失败计入分母 |

总量估算：单压缩阶段 6 臂 × 5 任务 × 3 重复 = 90 次运行；链阶段 2 臂 × 2 任务 = 4 次链运行。**若预算不足，先砍 B′+r 和 A 的重复次数，不砍 C 与 B′。**

## 七、失败分类

| 类别 | 判定规则 |
| --- | --- |
| F1 任务不可完成 | 同任务 A 臂也失败，且失败点相同 |
| F2 信息缺失 | 该查的没查（无冷层调用），且被问的信息确实在压缩范围内 |
| F3 状态错误 | 使用了旧版本/旧约束，可追溯到某条更早的来源 |
| F4 恢复失败 | 有冷层调用但未命中，或命中后用错 |
| F5 环境问题 | 工具/权限/超时，与压缩无关 |

每条失败必须归到一类，归不进去的记为"未分类"，未分类超过 10% 说明验收器设计有问题。

## 九、这轮能得出什么、不能得出什么

**能得出**：

- C 与 B′ 在同一触发点下，任务成功率与单位成功成本是否有差异
- 差异里有多少来自"材料"、多少来自"回查"
- 6 轮压缩链上是否出现累积退化

**不能得出**：

- 状态管理协议的独立贡献（无法单独关闭）
- 超出这五个任务结构的泛化结论
- 真实生产负载下的成本（合成任务的工具调用分布与真实不同）
- "WSC 一定更好"或"原生一定更差"——只报告在给定条件下的差值
