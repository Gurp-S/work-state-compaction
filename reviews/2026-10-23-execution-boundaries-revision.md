# 执行前绑定、日志缺口与数据库错误清理

本修订在 factual B/C 完成并封存之后实施。对照的运行时版本仍是 `versions/20261023-factual-view-v1.zip`；下面的新代码不能冒用旧资格回执。

结构性原因及修复：

- 只登记 pins 不等于执行时检查。保留进程入口现在先检查资格，再检查实际 pins 和冻结起点，之后才进入工作区/原生进程准备；每次模型阶段在发请求前再次检查，全部阶段结束后也检查。保留既有缺少 C 资格时的提前拒绝语义。
- 以前最终归档直接跳过不存在的 rollout，可能把证据缺口漏掉。独立 `native_thread_archive.py` 现在为每个已打开线程生成归档结果或明确错误；缺失计为未知，部分文件保留已知回执和原始字节，一个坏线程不妨碍其他线程归档。归档缺口使实验状态停止，不准进入资格封存。计数仍只是观察到的响应数，不反推缺失部分为零。
- CLI 对 sqlite3.Error 不走中性 JSON 错误出口，现纳入既有处理；仅输出异常类型，不回显数据库内部细节。
- 实际损坏数据库用例同时暴露 Store.connect 的连接清理缺口：PRAGMA 初始化在 try/finally 外，异常会遗留 Windows 文件句柄。现在连接创建后，初始化和使用都由同一 finally 负责关闭，不改变持久化级别。

验证：修复前 4 个入口/CLI 反例全部未通过，其中损坏数据库还导致临时目录清理失败；额外的连接初始化用例确认 close 调用为 0。新归档用例覆盖缺失、未完成尾部、无效完整行、归档再次读取失败及其他线程保留。最终独立包检查 **102/102** 通过，源哈希与明细在 `validation/execution-boundaries-20261023/suite-final.json` 和 `.txt`。

首次全套检查发现新文件校验顺序抢先于既有缺资格拒绝，已恢复“资格→pins→准备”的顺序；保留初次失败回执 `suite-after.*`，未改旧资格测试削弱约束。当前新增入口测试确认 pins 在工作区准备前拒绝，而不要求它先于资格检查。

未启动新的模型实验。本次也未降低 FULL 同步、修改原生 Codex、恢复/重跑旧失败、删除缺失证据或清理其他工作区。
