# 剩余优化空间：实测占比与方案

2026-10-27。上一轮做完 `rows` 去重复序列化、`stage` 复用来源、`file_digest` 之后，还剩多少可挖？先把每个阶段的钱花在哪量出来，再谈方案。

## 一、先量清楚

600 事件，单次 `stage` 2.78 s，`cProfile` 归因：

| 项 | 累计 | 占比 | 说明 |
| --- | --- | --- | --- |
| `nt.fsync` | 1.948 s | 70% | 每个证据对象落盘一次，728 次 |
| `_io.open` | 0.470 s | 17% | 1442 次，NTFS + 杀软的开文件成本 |
| `sqlite3.execute` | 0.044 s | 1.6% | 634 次查询 |
| `json.iterencode` | 0.033 s | 1.2% | |
| `sha256` | 0.011 s | 0.4% | |

单独量 SQL：`stage` 里 SQL 占 1.5%，`install` 里占 2.9%。

结论很直接：**CPU 侧的代码优化已经没什么油水了，剩下的是"每个文件两次内核调用"的结构成本。**

## 二、候选方案与判断

### A. SQL 批量查询（stage 的 324 次 SELECT、present 的 121 次）

- 做法：把 `source_row` 逐条查询改成一次 `IN (...)`，`presented` 的存在性检查同理
- 实测上限：`stage` 的 SQL 总共 0.044 s，全砍掉也就 1.5%
- **判断：纯收益，但收益 <1.5%，不值得单独做一轮**。可以顺手做，不值得为它改接口

### B. SQLite PRAGMA（`mmap_size` / `cache_size` / `temp_store`）

- 做法：`connect()` 里加三条 PRAGMA，不涉及持久化与并发语义
- 预期：官方与常见实践都推荐，但收益来自大库、大页缓存；本库只有几 MB，SQL 又只占 1.5%
- **判断：纯收益，但预计 <1%，属于"加了不亏"级别**。可以顺手加，但不要期待数字

### C. 去掉 `write_once` 的重复 `stat`

- 现状：先 `link_like(path)`（一次 `os.stat`）再 `open('xb')`；`open` 带 `O_EXCL`/`CREATE_NEW`，路径已存在时本身就会失败，失败分支里还会再查一次 `link_like`
- 做法：删掉入口那次预检查，只在 `FileExistsError` 分支里判定链接
- 实测上限：600 文件下 `nt.stat` 合计 0.069 s，砍一半约 0.035 s / 2.78 s
- 风险：可观测行为不变（链接仍然报 `evidence_path_symlink`，普通冲突仍然报 `evidence_object_conflict`）
- **判断：纯收益，约 1%，可以做**

### D. 并发写证据文件（线程池）

- 做法：`export_sources` 用 N 个线程并行写不同文件
- 预期：fsync 与 open 是阻塞的系统调用，理论上能并行；8 线程可能把 stage 的 2.78 s 压到 1 s 以内
- 代价：引入并发；失败时部分文件已落盘，错误语义从"整体失败"变成"部分失败"；GIL 下 CPU 部分不加速；错误路径与测试都要重写
- **判断：收益远大于负收益，但负收益不小（错误语义、可测试性）**。真要做，建议先做单线程的 A/B 拿到基线，再开一个开关做旁路验证

### E. 默认关闭逐对象 fsync

- 现状：`evidence_sync=False` 已经存在，默认 `True`
- 实测：`stage` 2.09 s → 1.26 s（−40%），整轮 −42%
- 代价：掉电时可能留下半截对象，重试会撞 `evidence_object_conflict` 需要人工清
- **判断：不是纯收益，是策略选择**。已有开关，默认值是否改由使用者场景决定，代码侧不建议动

### F. 合并导出文件（减少文件数）

- 做法：把所有证据对象打成一个归档，或按会话分片
- 预期：直接消灭 70% 的 fsync 与 17% 的 open，是唯一能上台阶的做法
- 代价：导出布局变了，内容寻址、逐文件校验、宿主读取方式全部要改
- **判断：改机制，不做**

## 三、建议

按"纯收益且值得动手"排序，只剩 C；B 可以顺手加但不承诺数字；A 不值得单独做。

真正的两个台阶（D 并发、F 合并文件）都不是纯代码优化：D 要接受错误语义变化，F 要改导出契约。如果目标是"更快的 stage"，只有这两条能带来数量级变化；如果目标是"不改机制地再榨一点"，那已经到边界了。

## 四、局限

- 所有占比来自本机 600 事件、单次 `stage`，fsync 与 open 的绝对值跟磁盘和杀软强相关；换 NVMe 后这两项的占比会下降，但"每文件两次内核调用"的结构不变。
- 没有测 `install` 的并发潜力，也没有测多线程下 fsync 的实际加速比；D 的收益目前是推算，不是实测。
