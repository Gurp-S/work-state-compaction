## 治本修复：两个短名体系发生同名异义

实际C数据中，展示层IndexedCheckpointAdapter按保留项排列生成s0、s1、s2；恢复层SnapshotSourceAccess按固定事件seq生成s1、s2、s3…。两者同名而非同源：

- C先读s0：展示中存在，恢复层却报source_access_source_not_bound。
- C再读s2：展示指最新policy/r2，恢复层合法返回seq=2的旧调用参数，内容并不是该展示名所指来源。

这不是温度能够解释的引用问题。结构性规则改为：选择、展示、恢复都采用snapshot固定事件序号，不再按本次选材重新编号。选材仍由模型决定；引擎只绑定明确ID与seq，不做语义推断、关键词排名或替换旧证据。

新逻辑先以独立policy与旧dense分支A/B：旧分支复现不存在/读错源；新分支所有显示短名读回准确来源，且不同选材中同源短名不变。4项检查通过，包含旧导出仍可原样展开；3项索引投影/篡改回归、2项宿主回执检查通过。之后新导出默认采用固定序号，旧dense策略仅保留复现/解码用途。发布前增加展示与恢复绑定检查，旧不兼容映射拒绝进入接收者，不自动修补。映射只保存热内容实际引用的ID，不另建全历史大小的映射表。

未重新调用模型验证性能；只能确认这项错误映射已被程序前后对照修复，不能量化声称它省去了原6次查询或多少Token。

## 另一个确定性问题：模型执行环境不能启动原Python

续接中py -3.11报No installed Python found，本机其他Python路径出现CreateProcessAsUserW错误5，随后模型继续寻找解释器并尝试了被禁的下载。不能将这些成本都算为WSC压缩损失。

零推理复现结果：直接调用已知Python3.11也被拒；仅添加源目录只读授权仍被拒；复制执行文件后能启动，但原位置标准库不可读；把现有Python与标准库置于工作区后，原生同类权限环境成功执行，返回version=3.11.9、unittest_available=true、sqlite_available=true、private_denied=true。没有网络下载、没有安装软件，没有修改系统Python。未证实有用的额外只读授权接口已撤回，避免保留无效机制。

工作区运行时复用本机已有文件，约23.9MB，原始材料保存在wsc-matrix-python-admission-20261028-v4；版本增量只保存其指纹及验证结果，不在每个版本重复存放二进制。该运行时尚未用于新B/C模型运行，后续必须给两臂相同配置和事实性工具信息。
