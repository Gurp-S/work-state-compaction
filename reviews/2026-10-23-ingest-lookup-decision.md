# 不合入事务内批量查询复用候选

复审指出逐事件重复查询来源 ID、call/result 身份，静态判断正确。本次在独立模块中预取当前批次相关身份（每次 SQL 最多 512 参数），并在实际插入成功后更新事务内集合；保留原有逐事件语义检查、INSERT、控制 epoch 更新和回滚。

八项旁路检查通过：同批 call/result 与精确重复、已有 call 接收结果、未来 call 不能满足前面的 result、冲突 ID 回滚、重复调用身份、重复结果身份、超过查询分块的重复接收、单遍迭代器的实时查询语义。新旧返回 ID、全部持久行、顺序和 epoch 逐项一致。

但查询次数不等于整体收益。2177 个输入项（2049 个不同事件、64 个已存在事件）的固定样本：

| 指标 | 封存旧代码 | 旁路候选 |
| --- | ---: | ---: |
| SELECT | 5155 | 9 |
| INSERT（含元数据） | 1986 | 1986 |
| 无追踪探针的完整事务中位耗时 | 66.434 ms | 66.547 ms |
| Python 新增分配峰值 | 42352 bytes | 472432 bytes |

最初 `sidecar.json` 同时计数 SQL 和计时，观察探针本身对旧方案多次回调，会夸大查询减少的时间收益；该原始记录保留，计时不作为准入依据。修正后的 `sidecar-no-trace.json` 将 SQL 计数、实际耗时、峰值内存分开测量，包含连接、事务和提交；旧函数直接来自封存版本，避免用另一个慢实现当基线。

结论：此样本没有事务耗时收益，分配峰值增加约 430 KB。**拒绝合入**，不因为 SELECT 数字漂亮而保留额外缓存机制。未来不同 I/O/批量规模可能不同，本次不外推所有场景无效。
