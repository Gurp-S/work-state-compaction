# WSC 设计归档（2026-11-19）：当前最佳版本 nosig

- 当前版本：`wsc_nosig` —— 阈值触发压缩 + EXT 提取契约 + 引擎值账本 + 条件化恢复契约。
- 对照对象：dsh 原生压缩（`dsh_native`）。
- 关联文档：[今日目标达成表](goals-20261119.md)、[重复采样与契约消融实验记录](wsc-repeat-sampling-20261119.md)、[明日目标讨论稿](goals-20261120.md)

## 一、一句话定位

WSC 不要求模型写“会话摘要”。模型只回答一个问题：**这一轮出现了什么引擎自己推不出来的关系**；检查点的排版、精确值、工作状态、证据索引和失效判定全部由引擎从事件里确定性生成。

## 二、设计原则

1. **约束先行**：模型只填引擎推不出的判断（决策、意图、原因），不写引擎能算的东西。
2. **最小充分**：能从事件导出的内容（值、编辑、检查、状态）一律不经过模型。
3. **时序分离**：压缩（记录关系）和恢复（执行下一步）分开计价、分开验证，不混为一个“摘要质量”。
4. **异常正确性**：失败、过期、未验证是状态的一部分，不让模型猜，也不写进正常答案里。
5. **按需深入**：只在上下文真的变大时压缩，不为每一轮都付一次模型调用。
6. **变更闭环**：每个新机制必须有离线不变量、重复采样和失败归因，才算进入默认路径。

## 三、流水线总览

| 阶段 | 谁做 | 产物 | 是否花模型 token |
| --- | --- | --- | --- |
| 事件导入 | 引擎 | 统一的事件流（消息、调用、结果） | 否 |
| 触发判断 | 引擎 | 压缩点：阈值 / 用户指令 / 高信号失败与决策 | 否 |
| 关系抽取 | 模型（EXT） | 本轮的新关系与修订，带消息引用 | 是 |
| 账本合并 | 引擎 | 当前有效关系，旧的标记 superseded / invalidated | 否 |
| 值账本 | 引擎 | `V1..Vn` 精确值行与词项 | 否 |
| 状态投影 | 引擎 | `done / open / next / unknown` | 否 |
| 检查收据 | 引擎 | 编辑 → 后续检查 → 版本绑定，过期可判定 | 否 |
| 排版 | 引擎 | 唯一一份自然语言 passage | 否 |
| 恢复 | 模型 + 引擎 | 动作 JSON；最多 3 回合，末回合禁止取回 | 是 |

## 四、每项设计：问题怎么发现、怎么解决、收益怎么判断

### D1 事件溯源账本与引擎状态投影

- **问题怎么发现。** 11-18 的检查点对照暴露了同一关系被写三遍：无检查同时进 `open` 和 `unknown`，`next` 同时出现在两处，检查又在独立 Checks 段重算；需求原文存三份并被截断；编辑返回错误也会被当成“已应用”。根因是模型和引擎都在写状态，而规则分散在两套实现里。
- **怎么解决。** 账本只存关系（`Understanding`：id、rev、status、sources、seq、invalid_when）；状态由 `engine_state` 从账本与事件推导（[live.py:1323](../benchmarks/coding_compaction_v1/live.py#L1323)）；编辑是否成功由收据判定（[live.py:958](../benchmarks/coding_compaction_v1/live.py#L958)）；需求在状态里只留位置引用 `req#N`，原文只在控制段逐字出现一次。
- **收益怎么判断。** 同场景对照：lean 总字节 −26.2%，State 452→184B，Checks 段 117→0；3 场景 6/6 成功、违规 0；离线断言覆盖“无锚点、失败编辑、req# 引用”。
- **边界。** 状态只回答“工作做到哪”，不承载语义判断；语义缺口仍由模型在抽取时决定是否记录。

### D2 阈值触发压缩，而不是每轮蒸馏

- **问题怎么发现。** 成本按调用拆开后看到：20 轮用例每轮一次蒸馏，压缩调用数随轮次线性增长，而大多数轮次没有新关系；高信号提示（gater）又被证明在阈值压缩时是冗余的（区域蒸馏本来就看到了失败与决策）。
- **怎么解决。** 未压缩轮次只累积 delta（[resume.py:237](../benchmarks/coding_compaction_v1/resume.py#L237)）；只有待压区域超过阈值（合成用例 32000 字符，约 8k token）或到达会话末尾才调用模型。没有显式阈值的短用例退回确定性门控：用户指令或高信号失败/决策触发，冷却 2 轮（[distillation_gate.py:57](../src/wsc/distillation_gate.py#L57)）。
- **收益怎么判断。** 20 轮用例从 20 次蒸馏降到 2 次；两模型 5 次采样均 5/5；成本与 native 的差距主要剩在“同样两次压缩里模型多想的那部分”，而不是调用次数。
- **边界。** 阈值是产品参数，不是压缩算法；阈值越高调用越少，但每次要处理的区域越大，需按上下文窗口另行定标。

### D3 EXT 提取契约：只抽取，不判断账本

- **问题怎么发现。** 早期契约要求模型“维护账本”：判断哪条该替换、哪条该失效、状态该进步到哪。一次调用要同时做抽取、判断和写作，推理量约为纯抽取的两倍，且容易把引擎能推导的缺口也写一遍。
- **怎么解决。** EXT 只要求“从编号区域里抽取引擎推不出的关系”（[live.py:176](../benchmarks/coding_compaction_v1/live.py#L176)）：最多 5 条新关系、3 条修订，一种关系一句、100 字符，引用消息编号，拿不准就不写。修订与失效仍由引擎合并（[resume.py:203](../benchmarks/coding_compaction_v1/resume.py#L203)）。
- **收益怎么判断。** 单次压缩调用的推理 token：DeepSeek EXT 2.1k，native 0.37k；GLM EXT 7.3k，native 1.9k——EXT 已经把“判断账本”的推理去掉，但与 native 的 Markdown 总结相比仍有差距，这部分是 JSON 契约与规则数量的固有成本。质量在两模型 × 两用例 × 5 次里保持 5/5。
- **边界。** 契约越短越省推理，但删掉“决策必须保留目标和所选标识符”会直接丢信息（见负结果 EXT2）。

### D4 引擎值账本：精确值零模型调用

- **问题怎么发现。** 检查点与恢复动作对照后发现两类事故：值被改写（数字、路径、错误串只剩大意），以及“提到了但没取到”——模型凭记忆写值。根因是值本来就在工具事件里，却让模型抄。
- **怎么解决。** 引擎从工具事件里抽精确值：跳过错误、测试结果、填充文本和重复项，生成稳定的 `V1..Vn` 行，带标签与检索词项（[coding_ledger.py:87](../src/wsc/coding_ledger.py#L87)）；被预算裁掉的值仍可按 `V` 键取回；恢复前可选地把只复述值的账本条目隐藏（[coding_ledger.py:119](../src/wsc/coding_ledger.py#L119)）。值段在排版里位于导航索引之前、按旧到新裁剪（[passage.py:59](../src/wsc/passage.py#L59)、[passage.py:112](../src/wsc/passage.py#L112)）。
- **收益怎么判断。** 值的产生与携带不再花模型 token；恢复阶段长用例 fetch 0–1 次；检查点保持在 1.6–1.9KB。离线不变量：键连续、来源唯一、所有必需标记在索引或值段可发现、用户原文不进入值段。
- **边界。** 引擎只抽工具事件里的值；助手决策里的标识符不是引擎可推导的，必须由模型写进关系（这正是 EXT2 失败的边界）。

### D5 恢复契约：条件化、可执行、末回合收敛

- **问题怎么发现。** 按调用解剖恢复阶段后看到三种浪费：模型先返回一个 read/fetch 回合再给答案；检查点没有值段时，契约仍在讲“Observed values 权威、不要为取值读文件”；GLM 的恢复推理可达 20–40k。
- **怎么解决。** 恢复契约按检查点内容组合（[resume_contract.py:16](../src/wsc/resume_contract.py#L16)、[resume.py:59](../benchmarks/coding_compaction_v1/resume.py#L59)）：只有出现 “Observed values” 段才加两条值规则；缺值取回、批量取回、状态覆盖即首回合直出、陈旧值禁用四条始终保留。循环最多 3 回合，末回合明确禁止 fetch/read（[resume.py:151](../benchmarks/coding_compaction_v1/resume.py#L151)）。
- **收益怎么判断。** 同一检查点、压缩调用复用缓存的消融：旧短提示 v1 与现行 v2 都 5/5，v2 恢复成本高 25%（¥0.0237 vs ¥0.0189）→ 条件化后无值段时两者等价；长用例恢复阶段 fetch 0–1 次；GLM 长用例在契约收紧后 5 次均值 ¥0.1404（旧契约只有单次 ¥0.1953，仅作方向对比）。
- **边界。** 契约只能约束动作与取值，不能约束模型内部推理；GLM 的推理风格问题按模型侧处理。

### D6 重复采样：收益判定的方法本身

- **问题怎么发现。** 同一个用例换一次运行就能得出相反结论：GLM native 短用例 5 次成本均值 ¥0.1384、标准差 ¥0.0616，区间宽度超过两臂均值差；“gater 更贵”“GLM 是 3.4×”这类单次结论都是噪声。
- **怎么解决。** `--repeat N`，每次重复用独立 `Model` 实例与缓存（[resume.py:483](../benchmarks/coding_compaction_v1/resume.py#L483)、[resume.py:617](../benchmarks/coding_compaction_v1/resume.py#L617)）；报告成功率、required、extra、violations、成本均值±sd 与区间、检查点大小；失败逐例归因 model / recovery / wsc。
- **收益怎么判断。** 五次采样把质量差异从“偶然”变成可复核：WSC 20/20，native 19/20；成本差异用区间是否重叠表述，而不是只看均值。
- **边界。** 重复采样不能消除模型侧方差，只能让结论匹配方差；样本数仍有限，极端尾部事件（如格式重试）需要单独计数。

## 五、被否决的设计（负结果也是设计的一部分）

| 设计 | 结果 | 为什么否决 |
| --- | --- | --- |
| 高信号提示（gater） | 阈值压缩时提示失败/决策行；两模型质量不变，DeepSeek 单次贵约 55% | 区域蒸馏已看到原文，提示只增加推理 |
| 每轮蒸馏 | 20 轮用例 20 次调用 | 成本随轮次线性增长，收益集中在少数高信号轮 |
| EXT2（引擎持值、模型只记决策） | 原版两模型 1/5（目标路径被省略）；补措辞后 DeepSeek 4/5、压缩 −49%，但 1/5 空账本 | 需要继续加硬规则才能稳定，收益不抵脆弱性 |
| tank（隐藏复述值的账本条目） | 能缩小呈现，但重复采样下没有稳定质量收益 | 不进入默认 |
| 降低 `max_tokens` 省钱 | 512/1024 直接空输出（推理先被截断）；GLM 不受上限约束 | 省不了推理，反而丢结果 |
| 用提示词压制推理 | 属于给模型行为打补丁 | 信息齐全而模型多想，归模型侧，不加机制 |
| 单次运行比较 | 结论会随采样翻转 | 已被重复采样口径取代 |

## 六、与 DSH native 的对比

### 结构

| 维度 | DSH native | WSC nosig |
| --- | --- | --- |
| 模型输出 | 固定 8 段的 Markdown 摘要（含 Next Step） | 最多 5 条关系 + 3 条修订的 JSON |
| 精确值 | 靠模型抄写 | 引擎从工具事件生成 `V` 键 |
| 工作状态 | 摘要里的文字段 | 引擎投影 `done/open/next/unknown` |
| 检查覆盖 | 摘要里描述 | 引擎收据绑定编辑与后续检查，可判定过期 |
| 证据 | 摘要文本本身 | 归档原文 + 短导航索引 + 取回键 |
| 保留策略 | 摘要替换旧段，尾部 16% 原文保留 | 关系账本去重 + 未压缩轮次直接累积 |
| 恢复契约 | 无（沿用会话提示） | 条件化动作契约，最多 3 回合 |

### 质量（两模型 × 两用例 × 各 5 次）

| 模型 | 用例 | native | wsc_nosig |
| --- | --- | --- | --- |
| deepseek-flash | silent-decision | 4/5 | 5/5 |
| deepseek-flash | silent-decision-long | 5/5 | 5/5 |
| glm-5.3 | silent-decision | 5/5 | 5/5 |
| glm-5.3 | silent-decision-long | 5/5 | 5/5 |
| 合计 | | 19/20 | 20/20 |

native 的唯一失败是模型侧：检查点已写明 `send_once`，该样本仍输出 `client.send`。

### 成本（每格 5 次均值±sd，人民币）

| 模型 | 用例 | native | wsc_nosig | 关系 |
| --- | --- | --- | --- | --- |
| deepseek-flash | 短 | 0.0429±0.0082 | 0.0725±0.0074 | 1.7×，区间不重叠 |
| deepseek-flash | 20 轮 | 0.0281±0.0060 | 0.0407±0.0080 | 1.45×，区间重叠 |
| glm-5.3 | 短 | 0.1384±0.0616 | 0.2105±0.0434 | 1.5×，区间重叠 |
| glm-5.3 | 20 轮 | 0.0727±0.0135 | 0.1404±0.0451 | 1.9×，区间基本不重叠 |

### 成本解剖（单次均值）

| 阶段 | DeepSeek native | DeepSeek nosig | GLM native | GLM nosig |
| --- | --- | --- | --- | --- |
| 压缩 | 0.0137 | 0.0202 | 0.0246 | 0.0621＋重试 0.0046 |
| 恢复最终回合 | 0.0094 | 0.0176 | 0.0355 | 0.0380 |
| 恢复中间回合 | 0.0050 | 0.0029 | 0.0127 | 0.0357 |
| 合计 | 0.0281 | 0.0407 | 0.0727 | 0.1404 |

- WSC 检查点只有 1.6–1.9KB（native 5.9–6.7KB），但 prompt 只占总成本 6–8%；差距来自模型推理 token。
- 压缩阶段：单次推理 DeepSeek 2.1k vs native 0.37k，GLM 7.3k vs 1.9k——EXT 的 JSON 契约仍比 Markdown 总结诱发更多推理。
- 恢复阶段：DeepSeek 最终回合 2.4× native；GLM 的中间回合因“先取回再回答”而变贵。
- native 的摘要自带 “Next Step”，模型恢复时推理少；WSC 的状态更短，模型要自己补出下一步，这是当前版本用推理换确定性的代价。

### 失败模式与归因

| 模式 | 谁的问题 | 处理 |
| --- | --- | --- |
| native 检查点有决策，模型仍写旧调用 | 模型侧 | 记录，不加机制 |
| WSC 检查点缺决策（EXT2 空账本） | 机制侧（契约过度删除） | 已放弃该设计，保留 EXT |
| 恢复阶段多余取回 | 混合：契约与模型风格 | 直出规则 + 条件化契约；不追着模型加提示 |
| GLM 推理超长、`max_tokens` 不生效 | 模型侧 | 600s 超时；按模型分别报告成本 |
| 解析失败重试 | 模型输出格式 | 已计数（GLM 3/50 调用），宽松修复待做 |

## 八、未验证与风险

- GLM 长用例成本仍是 native 约 1.9×，“成本不高于 native”未过线；DeepSeek 长用例只在分布层面重叠。
- 全部用例为合成会话；真实 20+ 轮仓库会话与人工 oracle 尚未采集。
- 短用例逐轮压缩是基架口径，生产短会话不会触发，成本比较只作方向。
- 多键取回与回合上限只做了离线断言，未专项压测。
- 生产路径（dsh-wsc）未接入值账本、门控与条件化恢复契约。
- GLM 有 3–6% 的解析失败重试成本，宽松修复未实施。
