# 分层压力评测首轮结果（2026-11-19）

- 关联计划：[当日目标达成表](goals-20261119.md)
- 今日达成：[今日目标达成表](goals-20261118.md)
- 模型：deepseek-flash；成本口径 cached 0.02 / uncached 1.00 / output 4.00 元每百万 token
- 运行目录：
  - E1 `benchmarks/coding_compaction_v1/runs/resume-20261119-094545`
  - 2A `benchmarks/coding_compaction_v1/runs/stress-20261119-094547`
  - 2B `benchmarks/coding_compaction_v1/runs/stress-20261119-095801`
- 三个进程并行执行，总花费约 ¥2.69，未超 ¥4。

## 一、结论

1. **成本目标没有达成。** 在 6 轮常规场景上，native 每成功任务 ¥0.0318，WSC ¥0.1101、thin ¥0.1868、lean ¥0.2009。native 以 3.5 倍的成本优势与三臂持平或更好。
2. **差距来自输出 token，不是 checkpoint 体积。** WSC 系列 checkpoint 只有 3.4–5.4KB，native 12.2KB；但 WSC 的压缩输出是 17k–51k completion token，native 只有 3.8k–5.6k。账本写作本身是费用主体。
3. **分层评测目前仍以触顶为主。** 2A 的 L1–L4、2B 的 all-on 全部通过，唯一的行为差异在 base：lean 漏掉 OWN3（2/3）。
4. **2B 的“native 违规 5 次”是误报。** native 把 STL8/CMP1/CMP2 写在“已丢弃”的说明里，被字面匹配当成使用；修正为否定语境不计入后，所有臂 0 违规、0 stale。
5. **治理层在当前强度下没有衰减。** L4 硬约束全部存活，控制组同样零违规；软偏好所有臂（含控制组）都没遵守，属于模型侧，不是压缩导致。

## 二、E1：四臂 6 轮对照

| 臂 | 成功 | 必需命中 | 违规 | 多余 | 字节 | 总成本 | 每成功成本 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| native | 3/3 | 3/3 | 0 | 3 | 12249 | ¥0.0955 | **¥0.0318** |
| wsc | 3/3 | 3/3 | 0 | 2 | 4382 | ¥0.3302 | ¥0.1101 |
| lean | 2/3 | 2/3 | 1 | 5 | 3400 | ¥0.4018 | ¥0.2009 |

- lean 的失败是模型侧：checkpoint 已写 `next: append release marker REL-9482 to docs/relnotes.md`，模型仍编辑 `src/flags.py` 并运行 grep，归因字段 `stated=2/2`。
- native 的 checkpoint 更大，但它的压缩调用只写 4k 级 token；WSC 每轮重写账本，输出成本是 native 的 4–9 倍。

## 三、2A：分层单开（native / lean / 控制组）

| 层 | native | lean | 控制组 | 说明 |
| --- | --- | --- | --- | --- |
| base | 3/3 | **2/3** | 3/3 | lean 丢失 OWN3 |
| L1 位置/间距 | 3/3 | 3/3 | 3/3 | 触顶 |
| L2 语义稀释 | 3/3 | 3/3 | 3/3 | lean 丢弃矛盾/碰撞片段，native 全保留 |
| L3 系统扰动 | 3/3 | 3/3 | 3/3 | 无 stale 使用 |
| L4 治理 | 3/3 | 3/3 | 3/3 | 控制组也零违规；软偏好全未遵守 |

2A 总花费 ¥0.7256。lean 的单位成本在 2A 为 ¥0.066–0.147/例，仍高于 native 的 ¥0.024–0.038。

base 的失败有两层原因：

- 模型在最后一轮拿到了 `owner code is OWN3`，但账本写成 “owner code is not shown”，是模型遗漏；
- 4KB 预算先裁剪索引，tail 来源被裁掉，导致续接模型也无法取回。模型遗漏是根因，预算裁剪把它放大成不可恢复。

## 四、2B：all-on（10 轮，四臂 + 控制组）

修正误报后：五臂全部 3/3 命中、0 违规、0 stale，全部保留四层标记，总花费 ¥0.5763；成本 native ¥0.0650，WSC ¥0.1429，lean ¥0.1972，thin ¥0.1587。

这轮没有出现层间耦合导致的失效。原因有两个：

1. 治理约束放在用户消息里，WSC 的 Control 逐字保留，native 的摘要也没有丢；
2. 位置、稀释、扰动的正确值都能从少量片段推出，压缩后仍然够用。

## 五、评测本身修掉的两个缺陷

1. **“提及”被当成“使用”。** 自动评分把动作里“已丢弃 STL8/CMP1/CMP2”的说明算成 stale 使用与违规，native 因此被误判 5 次违规。修正：marker 出现位置的 ±90 字符内如有否定/丢弃语境，不计入使用。
2. **flip 对格式过敏。** 原实现比较完整 JSON 签名，动作正确但措辞不同就会 flip。改为结果级签名：成功、必需命中、违规数、实际使用 marker 集合。旧 run 未保存控制组动作，重放时 flip 记为未知。

## 六、第二轮：关系型账本成本对照

运行：`resume-20261119-105809`；臂 `native / wsc / wsc_rel`，3 场景 × 6 轮，花费 ¥0.7906。

| 臂 | 成功 | 违规 | 多余 | 字节 | 压缩输出 token | 总成本 | 每成功成本 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| native | 3/3 | 0 | 3 | 12200 | 12696 | ¥0.0867 | **¥0.0289** |
| wsc | 3/3 | 0 | 2 | 4396 | 91762 | ¥0.4170 | ¥0.1390 |
| wsc_rel | 2/3 | 0 | 4 | 4101 | 57753 | ¥0.2869 | ¥0.1435 |

- 关系型合同把压缩输出从 91.8k token 降到 57.8k（−37%），总成本 −31%；但 `reversed-late` 失败，导致每成功成本反而略高于 WSC。
- 失败是模型侧行为：checkpoint 的 `State: open: req#3; latest edit … wrote "round 6 change"` 与 Control 中第 3 条变更都写明要改成 async，模型只运行了测试，没有编辑文件。
- 归因字段判为 `recovery`（`async def export` 只在源码索引里），但语义要求本身已在 Control 中；这是 `req#3` 间接引用需要模型回查造成的，不是信息缺失。
- 结论：关系型账本确实省输出，但“禁止重述需求”让模型必须解析 `req#N`；这是可以修的合同问题，不是机制失效。
- 成本结构：按每例压缩输出计，native 约 4.2k token，rel 约 19.3k，WSC 约 30.6k。即使把渲染成本降到零，压缩调用本身仍是 native 的 4 倍以上，因此“只写关系”只能缩小差距，不能在当前调用节奏下追平 native。

## 七、第三轮：硬化 2A（治理进工具输出 + 8 片段 + 动作级扰动）

运行：`stress-20261119-111434`；5 配置 × (native / lean / rel + 控制组)，6 轮，花费 ¥1.0036。

| 配置 | native | lean | rel | 控制组 | 备注 |
| --- | --- | --- | --- | --- | --- |
| base（8 片段） | 8/8 | 8/8 | 8/8 | 8/8 | 触顶 |
| L1 位置/间距 | 8/8 | 8/8 | 8/8 | 8/8 | 触顶 |
| L2 语义稀释 | 8/8 | 8/8 | 8/8 | 8/8 | rel 主动丢弃矛盾/碰撞片段 |
| L3 扰动 | **0/8** | 8/8 | 8/8 | 8/8 | native 恢复回路失败 |
| L4 治理 | 8/8 | 8/8 | 8/8 | 8/8 | 无衰减 |

- **8 片段没有逼出取舍。** 所有臂都能从账本/索引拼出 8 个值；State 单桶 6 条的上限没有造成丢失。
- **治理层仍未衰减。** 策略现在只存在于 `docs/policies.md` 的工具输出里，但三臂与控制组都保留并通过；软偏好所有臂（含控制组）都没遵守，属于模型侧。
- **L3 是唯一分离点。** native 的摘要写着 `docs/policies.md: still unread; blocks writing`，模型把续接回合花在重读策略上，没有写部署说明；控制组和其他臂都完成。根因是压缩摘要产生了一个虚假的 pending 状态，随后模型照着它走。
- **rel 的选择性可观测。** L2/L3 中 rel 丢弃矛盾与冲突片段（retention 0.0），仍 8/8 通过；native/lean 保留全部。
- **成本**：native 每例 ¥0.031–0.041；rel ¥0.034–0.075，base 已接近 native；lean ¥0.074–0.117。

## 八、第四轮：硬化 2B all-on（10 轮，四臂 + rel + 控制组）

运行：`stress-20261119-112739`；花费 ¥0.8359；六条链并行。

| 臂 | 成功 | 必需命中 | 违规 | 字节 | 成本 | 说明 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| native | 0/8 | 0 | 0 | 5521 | ¥0.0878 | 输出裸 action 对象，不是 `{"actions":[…]}`，格式失败 |
| wsc | 8/8 | 8 | 0 | 3536 | ¥0.2287 | COL5 与 OWN3 并列标注，不构成替代 |
| lean | 8/8 | 8 | 0 | 3391 | ¥0.1554 | |
| rel | 8/8 | 8 | 0 | 2857 | ¥0.1854 | 丢弃冲突片段，仍通过 |
| thin | 8/8 | 8 | 0 | 2455 | ¥0.1604 | 丢弃冲突片段，仍通过 |
| control | 8/8 | 8 | 0 | 50738 | ¥0.0181 | 上限 |

- native 的失败是模型侧输出格式，不是压缩丢信息：checkpoint 已含 8 个值、策略和冲突说明，模型只返回了裸 action 对象。
- WSC 原先的 1 次违规是规则过严：模型把 `COL5` 标为 “on-call rotation owner code”，同时给了权威 `OWN3`。已改为“只有替代权威值才算违规”，重放后违规归零。
- rel 与 thin 在长程耦合中丢弃了冲突片段（conflict retention 0.0），但 8/8 通过，说明当前强度下丢弃冲突值没有反噬。
- 结论：硬化后的 all-on 仍未产生“压缩导致质量下降”的证据；唯一失败来自模型的格式遵从，不属于 WSC 机制。累计花费约 ¥5.32。

## 九、下一步建议

1. **把治理约束移出用户消息**，放进工具读取的策略文件，否则 WSC 的 Control 永远免疫，测不到账本/索引是否保留约束。
2. **增加必需片段数量，超过账本条目与状态行上限**，迫使压缩做真正的取舍；当前 3 个片段太少。
3. **让扰动的结果改变正确动作**，例如 stale 值与当前值指向不同文件，而不是只在说明里出现。
4. **成本优化回到账本**：减少每轮重写量，或让 WSC 只写关系、不写散文；这比继续压缩 checkpoint 更直接。
