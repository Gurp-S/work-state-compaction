# dsh-wsc 生产对话对比（二）：nosig 呈现完整移植后 vs dsh 原生压缩（2026-11-21）

- 目的：验证「把 nosig 的检查点呈现完整移植进 dsh-wsc」之后，生产会话里的压缩次数、成本、压缩后连续性与测试完整性是否回到参考实现的水平。
- 前置：2026-11-20 的第一次有效配置对比（见 `dsh-wsc-production-ab-20261120.md`）中，WSC 压缩次数 9 vs 原生 8，但成本高 28%。原因是当时检查点是「分节拼接」的产物（工作集、最近工具输出、工具调用、文件清单都整段保留），中位 11.8k 字符，比原生还大；同时抽取按分段调用，9 次压缩有 8 个缺口。
- 模型：`deepseek-flash`（new-api，reasoningEffort low）。
- 窗口：`contextWindow 32768 / maxTokens 8192`（可用 24576）。
- 触发：WSC `capacityPercent 100 / warnRatio 0.6 / forceRatio 0.8 / retainRatio 0 / minReclaimRatio 0.15`；原生 `thresholdRatio 0.6 / headroomTokens 0 / retainRatio 0.16`。
- 驱动：headless 逐轮调用，同一游标续跑；25 轮脚本化仓库任务（10 个文件的 orders-report CLI），第 25 轮为「不读文件、不跑命令」的连续性探针。
- 数据：WSC 干净重跑 `.tmpfloor/prod-eval/out-a3`；原生 `.tmpfloor/prod-eval/out-b2`。另有一次同样代码、但在跑动中改了一句呈现前缀的 `out-a2` 作为第二样本。

## 这次移植了什么

检查点不再是一堆分节，而是一段有固定顺序的段落（与参考实现的 passage 同构，只把「模型读哪里」换成 DSH 的形态）：

1. 用户要求逐字引用，跨压缩累积，不随被遮蔽范围缩小；
2. 账本句子按 Constraint / Requirement / Decision / Verification / Context 排序并去重；
3. 工作状态（done / next / open、unknown），采用 DSH 能解析的状态块，同时是本次会话的交接状态；
4. 机械核对：最近四条「哪个文件在第几次编辑后由哪条命令检查」；
5. 引擎值账本：每个含精确值的结果一行，新的在前，只保留最新的 16 条，被裁掉的键会点名；
6. 证据索引：每类来源至少留一个入口（命令、编辑、测试、错误、笔记、结果），带 `seq` 便于 `read_history` / `read_evidence` 取回；
7. 超预算时先丢索引，再丢旧值，最后丢最低等级的账本条目；用户要求与状态不裁剪。

配套的引擎侧变化：抽取改为整段一次调用（超长才分段）并只重试一次；账本、值账本、状态投影、索引全部零模型调用；控制文本写入会话账本（`op: 'control'`），重启后仍能续上；工具回报的绝对路径统一换回工作区短路径，状态匹配同时接受短路径与绝对路径；压缩引擎自己注入的用户角色提示（"automatically generated checkpoint…"、60%/80% 压力提示）和「只运行/只汇报」的探测轮不会被误判成待办需求。

离线验证：`npm test` 204 项全过，其中 passage / 证据索引 / 状态投影 / 值账本均有独立用例。

## 结果（干净重跑，25 轮）

| 指标 | WSC nosig（移植后） | 原生 | 比值 |
| --- | --- | --- | --- |
| 压缩次数 | 6 | 9 | 0.67× |
| 检查点字符（中位数/范围） | 7.3k / 5.1–8.6k | 6.5k / 5.8–7.6k | 1.13× |
| 单次回收 token | 7.6k–10.7k | 6.6–8.3k | — |
| Agent prompt（未命中/命中） | 150k / 1512k | 242k / 1322k | 0.62× / 1.14× |
| 压缩调用 token（入/出） | 67k / 7k | 102k / 18k | 0.65× / 0.41× |
| 总成本当量（未命中 1.0、命中 0.02、输出 4.0 元/百万） | ¥0.310 | ¥0.393 | 0.79× |
| 墙钟（25 轮） | 626s | 731s | 0.86× |
| 最终测试 | 20 passed | 20 passed | 持平 |
| 连续性探针 | 5 问全对，0 次读文件，1 步作答 | 5 问全对，0 次读文件 | 持平 |

探针问题：TAX_RATE、默认行数环境变量、`summary(rows)` 的字段、最新两条 CHANGELOG、toCsv 是否允许负值。两臂都只凭检查点回答；WSC 的检查点里能直接看到 `TAX_RATE = 0.07`、`summary(rows) returns {count, totalCents}`、`toCsv` 对负值抛错等条目。

第二样本（`out-a2`，同一段代码、中途改过一句账本前缀，并在第 21 轮遇到评测服务端 503 后重启续跑）：压缩次数同为 6，成本 ¥0.356，探针同样全部答对（第 1 步就给出答案；随后收到 60% 压力提示，最后一条消息变成 "Ready for the next instruction."，所以按「最后一条消息」取探针会读到空回答）。两次 WSC 样本的成本落在 ¥0.31–0.36，原生为 ¥0.39。

## 与上一轮（分节检查点）的差别

- 压缩次数 9 → 6：检查点从 11.8k 字符降到 7.3k，压缩后留下的上下文更小，下一次触发更晚。
- 压缩调用输出 46k → 7k：整段一次抽取 + 一次重试，9 次压缩 8 个缺口降到 6 次压缩 3 个缺口（每次 1–2 条条目被拒，不影响交接）。
- 成本 1.28× → 0.79×：分节检查点把工作集和最近工具输出整段保留，缓存 prompt 被推高；段落式检查点只保留结论、精确值索引和状态，未命中 prompt 降到原生的 62%。
- 墙钟 1.47× → 0.86×。

## 仍然存在的现象

- 60% 压力提示会让模型在压力刚过线时花一步主动调用 `compact_context`（`out-a2` 第 16 轮、探针轮都出现过）。它换来更早、更小的一次压缩，但会让当前任务晚一步完成；是否保留由生产配置决定，移植本身不改变这一行为。
- 账本抽取仍会拒绝少量条目（`literal` 校验要求条目里的路径、数值、标识符出现在被引用的消息里）。6 次压缩共拒绝 6 条，其中一次整段没有可用条目，检查点仍正常发布。
- 状态块里的「no active requirement matched it」是机械回执：最后几轮的用户要求没有点名带扩展名的文件路径，状态无法把它们和某次编辑对上，就如实标为未核对，而不是猜成完成。

## 结论

完整移植后，WSC 在生产会话里以 0.79× 的成本、0.67× 的压缩次数完成同样的 25 轮任务：两臂最终测试都是 20 项全过，CLI 输出一致，不读文件的连续性探针都答对。上一轮 1.28× 的成本劣势来自分节检查点，而不是 nosig 机制本身。
