# 生产矩阵结论：WSC nosig 是否真实超过 dsh 原生压缩（2026-11-21）

## 问题

上一轮 25 轮单场景 A/B 得到 6 vs 9 次压缩、0.79× 成本，但样本只有一次。本轮要回答两件事：

1. 换任务类型（新功能、长程、重构、缺陷修复）、拉长轮次（16–40 轮）、并发重复采样之后，WSC 是否仍然赢原生压缩。
2. 基座的本质性缺陷修完后，两个候选优化（控制原文上限、passage 工作集）是否应该并入默认。

## 方法

- **场景**：`feature-25`（25 轮新功能，5 个探针事实）、`long-40`（40 轮，6 个探针）、`refactor-18`（18 轮模块重构，5 个探针）、`bugfix-16`（16 轮，注入 3 个缺陷并预置失败测试，6 个探针）。
- **臂**：
  - `native`：dsh 出厂 `compaction-basic`（60% 触发、保留 16%、摘要 4096 token）；
  - `wsc`：nosig passage 基线，`controlMaxBytes=0`、`passageWorkingset=false`；
  - `cap`：仅开 `controlMaxBytes=6000`；
  - `ws`：仅开 `passageWorkingset=true`（v2 工作集）；
  - `fix`：两项同开。
- **运行**：46 次（主矩阵 30 + 归因 16，`feature-25/ws` 有一次因模型工具调用 JSON 损坏从零重跑）。每次运行是独立轮次进程、共享 session，同一 `deepseek-flash`、32k 窗口、8192 输出预算、`--permission-mode workspace-write --approval-policy never`。profile：`native-eval` / `wsc-eval` / `wsc-cap` / `wsc-ws` / `wsc-fix`（插件目录均为指向工作区 `dsh-wsc` 的 junction）。
- **验收**：每次运行结束跑一次 `node --test`；末轮无工具、无读文件的探针回答 5–6 个事实。
- **成本模型**：¥1 / ¥0.02 / ¥4 每百万 token（未缓存输入 / 缓存输入 / 输出）。46 次运行合计 ¥10.80。

### 成本结构

WSC 相对原生最大的节省来自未缓存输入：原生每次压缩后的摘要作为普通消息在后续每轮重发，长程场景未缓存输入 ¥0.306，WSC 为 ¥0.022–0.032。输出 token 在两边都是主体：原生占 53–57%，WSC 占 72–82%。因此成本比主要由“压缩次数 × 每轮未缓存摘要”和“总输出/回合数”共同决定。

## 结论

1. **WSC 基座在四个场景全部低于原生压缩**，中位成本 0.47×–0.85×，长程收益最大，短缺陷修复最小但仍有 15% 优势。压缩次数约为原生一半（5/10、22/36、11/15、3/4）。
2. **正确性没有退化**。46 次运行的 `node --test` 全部通过；46 次探针中 40 次满分，6 次 5/6 缺的都是 `TAX_RATE=0.07`，分布在 native（1 次）、wsc（1 次）、fix（2 次）、cap（1 次）、ws（1 次）。原因是这些运行从未读过 `src/store.js`（0.07 只在该文件首行），不是压缩丢失；在读过该文件且值账本捕获的运行里，末轮都能直答。
3. **两项候选开关不并入默认**：
   - `controlMaxBytes=6000` 只在 `refactor-18` 有可辨收益（0.80× 于 wsc），`long-40` 持平（0.98×），`feature-25`/`bugfix-16` 也持平；收益方向存在但不稳定，且会省略最旧控制原文，有丢失早期约束的风险。
   - `passageWorkingset` 在所有场景与基线持平（0.90–0.98×），没有一致减少读文件回合（长程 read 95–127，基线 105–135；shell 47–80 vs 51–76），还让检查点更大（长程中位 15.3k vs 14.8k、`feature-25` 10.3k vs 7.9k）。假设“补文件正文能减少重读”没有得到支持。
   - 合并包 `fix` 因此不是稳定增益：`refactor-18` 0.83×、`long-40` 0.95×，但 `feature-25` 1.05×、`bugfix-16` 1.11×。
4. **已并入默认的是本质性修复**，并由本矩阵验证：值账本跨压缩持久化（`op:'value'`、全局 `V<n>`、文本去重）、状态/路径/引擎合成通知修正、抽取拒绝原因直方图。默认配置保持 `controlMaxBytes=0`、`passageWorkingset=false`。
5. **残余问题**：
   - 采样方差仍大（`refactor-18/wsc` 0.187–0.323，其中一次运行手工调用 `compact_context` 4 次）；
   - 输出 token 已占七到八成成本，继续压检查点体积的边际收益有限，下一步应针对回合数与输出；
   - 60% 压力提示偶尔多花一回合（触发策略问题，非 passage 缺陷）；
   - 4 次探针缺失提醒：验收事实必须确保在会话中被读到，否则测到的是任务脚本的覆盖盲区。

## 复现

```bash
cd experiments/prod-matrix
python matrix.py run --jobs 3 --repeats feature-25=2,long-40=2,refactor-18=3,bugfix-16=3 --arms native,wsc,fix
python matrix.py run --jobs 3 --repeats feature-25=2,long-40=2,refactor-18=2,bugfix-16=2 --arms cap,ws
python matrix.py analyze

```

## 后续优化（同日晚）

逐份检查点原文暴露了评分没显示的问题：87% 的长程检查点状态块为空，60% 压力提示会让最终消息变成空话。修复后（跨区间需求投影、Recent changes、最新请求横幅、warnRatio 0.8），同日对照长程成本 ¥0.459 → ¥0.429，空状态 87% → 9.6%，最终回答 3/3 一步交付。详见 `optimization-20261121.md`。
